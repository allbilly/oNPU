# Qwen2.5 sustained-request diagnostics

The ordinary aging run shows real thermal and NPU frequency drift alongside slower requests. Over 24 ordinary requests, the median of requests 0–2 versus 21–23 shifts from **374.5 to 410.4 ms TTFT**, **16.38 to 15.00 decode tok/s**, and **341.8 to 311.9 prefill-proxy tok/s**. Total request median rises from 4.214 to 4.617 s. This is a diagnostic sequence, not a qualified throughput cohort: the aging JSON has no warmup/measured flag, so these are index windows, not warmup and measured groups.

Thermals are reported separately by zone because zone0 is not always the hottest. Aging request 0 start readings are zone0 70.230°C and all-zone max 70.230°C; request 23 start is zone0 80.384°C and max 81.307°C. At each request’s first snapshot, zone0 rises from 75.769°C to 84.076°C, while the all-zone maximum is 79.461°C then 85.888°C (zone1/zone2). NPU devfreq is 1,000 MHz at request 0, then 800 MHz from request 8 through request 23. CPU policy clocks fluctuate rather than staying pinned: request 0 first snapshot reports policy0/4/6 at 1.800/2.256/2.256 GHz; request 23 reports 1.200/1.800/1.800 GHz. These are sysfs frequency readings, not physical-clock measurements.

The aging report records native replay and its diagnostic graph profile is dominated by native ROCKCHIP INT8 operators. Per-decode coarse timer medians from the first three requests are 58.463 ms runtime and 57.359 ms C; for the last three they are 64.574 and 63.286 ms. The runtime-minus-C gap changes only 1.104→1.292 ms while C time rises by about 5.927 ms. This does not support growing Python overhead as the main cause; native compute and board operating conditions are the stronger evidence.

The mixed runtime screen marks 12 requests `warmup: true` and 24 `warmup: false`; medians are split strictly by that flag in the [machine-readable summary](benchmark-qwen25-sustained-diagnostics-v1.json). Measured blocks use a mirrored order (normal/held/scalar1/scalar4/scalar4/scalar1/held/normal), but nonlinear drift and graph interactions still confound the comparison. Ordinary block0 has 392.238 ms TTFT / 326.332 prefill tok/s, while the final ordinary block7 has 763.078 ms / 167.742 tok/s. The runtime report has no thermal telemetry; the separate aging report confirms sustained-run thermal and frequency drift. Held does not establish a durable whole-request advantage; scalar1/4 do not establish a repeatable win, and scalar4 has especially poor measured TTFT and prefill proxy. None is promoted.

The three worker scheduling studies remain unpromoted: single-worker parking was modest and inconclusive, phase parking lost, and the held CPU5/7 mask lost. See the [phase-parking summary](benchmark-qwen25-idle-phase-v1.json) and [held-mask summary](benchmark-qwen25-held-mask-v1.json). The rejected prototype was removed from production after its pre-experiment hashes were checked against HEAD; no new CPU arithmetic was promoted. The latest actual HTTP/API result remains 323.32 prefill tok/s and 15.82 decode tok/s in the [API qualification summary](benchmark-qwen25-api-fast-prefill-v2.json). The passive SDK shape-capture lease is active. Correlated sysfs temperature and frequency readings describe the observed runs but do not establish thermal-throttling causality.

Raw report SHA-256 receipts and schema paths are recorded in the diagnostic JSON summaries. No model/device run was performed to produce this note.
